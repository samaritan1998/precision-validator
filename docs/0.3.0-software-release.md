# Version 0.3.0 software verification

**Software verification passed for the frozen 0.3.0 wheel.** This is the final
software distribution, with model numerical verdicts reported separately.
The baseline matrix still has six `numerical_failure` results; none was relabeled
as a model pass. The software qualification plan registered these diagnostic
outcomes before the new wheel's GPU execution. Numerical thresholds did not change.

Wheel: `precision_validator-0.3.0-py3-none-any.whl`

SHA-256: `c5fefbf9e861e7bc08a41dc6a0ed15fc9a31743ea261f430239f9cd8badc2be8`.

The runtime differs from rc3 only in the version string. All 69 package files
in the final source match this wheel, and the results below come from fresh
executions of this wheel. Previous rc3 runs do not substitute for these checks.

The independent audit recalculates full canonical gradients and updates for
every small native case, full parameters/master weights/Adam state vectors for
trajectory cases, and declared forward observations. It checks raw-file hashes,
fragment coverage, completion seals and real step counters. This does not
independently prove a framework's canonical mapping for every future model.
Independent native-state and mapping tests supply the separately documented
fixture-specific coverage.

HF integration checks contain two different outcomes: FP32 eager-versus-SDPA
backend comparisons pass their declared policy; BF16 compute examples remain
`report_only` without a model policy. Their adapter tests pass because captured
gradients and actual updates exactly match independent ordinary training.
`report_only` is never a numerical pass.

The first B200 allocation completed the matrix and extended tasks, then returned
to Pending with a stopped heartbeat. Those completed task receipts were retained;
FP32 wgrad and invariance were run in a fresh allocation with the same frozen
wheel, inputs, runners and gates. The incomplete attempt is not counted as a
passed execution. The platform interruption cause was not confirmed.

## Remaining numerical findings and limits

The historical combined BF16 TP/PP/EP test still fails even with native FP32
weight-gradient accumulation. The earlier real Qwen 256K TP2/CP2 comparison is
also unresolved. Its complete rc3 report is preserved; this release does not
claim a new 0.3.0 production 256K execution. Releasing the tool does not establish
numerical equivalence for either configuration.

Current Slime entry scope is synchronous text SFT from fresh weights, first N
optimizer steps, and one model chunk. It compares complete gradients, actual
updates and loss, and checks Adam state dtypes, finiteness and counters. Full
state-vector comparison and same-topology checkpoint resume belong to the
separate trajectory adapter. RL, multimodal, virtual pipeline, arbitrary model
support and long-run convergence are outside the verified scope.
